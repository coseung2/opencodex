# Kiro relay retries, terminal streaming, and Claude web tools

- Date/timezone: 2026-10-11, Asia/Seoul; investigated from about 08:12 KST.
- Symptoms: after tool work, a Kiro session repeatedly received local `502 relay_unavailable` and eventually answered; its terminal answer appeared as a batch. Built-in WebSearch/WebFetch results reported usage limits while the user reported their Anthropic weekly quota exhausted.
- Evidence: recent client retry records contained `relay_unavailable`, with up to five automatic retries; corresponding VM records included early thread-negotiation HTTP 400 and successful Kiro turns. Exact transport errno was not retained, so upload/early-response racing remains an attribution hypothesis, not a packet-level proof. The local edge streams requests through a raw HTTP/1.1 relay. OCX's configured general search backend was default OpenAI, not Anthropic. Built-in tools are separate helper requests and did not necessarily use that sidecar.
- Response: locally negotiate message threads after routing/binding validation, preserve native passthrough, send finite length-delimited relay uploads, and preserve an available early HTTP response over upload errors. No automatic side-effect replay was introduced.
- Streaming: incrementally decode the Kiro private terminal answer string while maintaining full JSON validation, memory admission and non-retryability after visible partial output. Ordinary commentary remains held so a completion tool can supersede it without duplicate text.
- Search: identify only Claude's dedicated WebSearch helper prompt plus hosted tool declaration, route it through the bound GPT-6.1 Sol model, remove native credentials, preserve hosted forced-tool choice, admit the current hosted selector in the Responses schema, and request/translate source lists. Ordinary native Claude requests, security classifier calls and WebFetch are not broadly remapped. Unavailable helper routes fail closed.
- Rollout: backup/hash/link-check guarded VM patches and a dedicated local runtime swap, with only the local supervisor/worker restarted and detached data relay preserved. Original settings stayed byte-identical. Short service restarts could make Notch metadata temporarily disconnected until its normal refresh; that is deployment interruption, not evidence that the provider was down.
- Verification: focused stream/edge/worker tests passed 129 cases; search/translation tests passed 71 cases after selector fixes. Actual authenticated local -> relay -> VM Kiro test returned HTTP 200, 58 text deltas and `end_turn`. WebSearch helper returned HTTP 200 with server search call/result blocks, 33 explicit source results and `end_turn` after source-preservation fixes. Protocol fallback probes pass on both inference/token-count endpoints. TypeScript/privacy/full-suite outcomes are reported separately.
- Remaining: end-user UI timing and repeated-request behavior need observation after the patch. No claim that every `502` cause is eliminated. Native WebFetch still depends on native usage limits; no blanket credential/provider override or quota bypass was installed.
- Final checks: focused integrated run passed 228 tests; a later helper-prefix/stream decoder run passed 16. Twelve consecutive authenticated local thread-negotiation probes returned the intended fallback without 502. The full-suite run completed all 12 batches with zero failures; final search selector/source additions were also checked with focused tests and live retrieval. Installed local and VM file hashes match the intended sources. Settings are preserved and service health is HTTP 200.
- Subsequent user-directed update: WebSearch helper and general web-search sidecar now select `gpt-6-luna` instead of GPT-6.1 Sol/default GPT-5.6 Luna. The dedicated helper remains bound to the current connection but does not expose hidden Luna as another main-session picker row. A live request returned HTTP 200 and 18 source results; VM logs reported requested and resolved model `gpt-6-luna`, with completed status. Vision settings and native Claude requests remained unchanged. The user requested only an audit of other quota-bearing helper functions, not their migration.
